# P07-T03 — Step 0 contract findings (2026-11-23)

- Inventory (`contexts/inventory/application/adjust-stock.ts`): `findBalancesOrdered` is a sorted Prisma `findMany`, **not** `FOR UPDATE`. Missing receipt balance is inserted as zero via `createMany(skipDuplicates)` before increment; missing issue balance throws `DomainError("INSUFFICIENT_STOCK", 409)` without requested/available details. `openStockBalance` delegates to `adjustStock`. T03 must lock sorted balance rows and translate insufficient stock to 422 with details; receipt uses existing port.
- Pipeline (`platform/http/pipeline.ts`, `platform/http/idempotency.ts`): lookup happens after authorization, before domain/version guard. Completed response JSON is persisted and returned on replay. Claim, domain, outbox, and completion share transaction; failed commands roll back claim and can retry with same key. Same scoped key with different payload throws 409 `IDEMPOTENCY_CONFLICT` while unexpired.
- Bridge (`platform/workflow/approval-service.ts`, `tests/platform/workflow-bridge.integration.test.ts`): submit uses `createRequest(tx, {documentId, submittedDocumentVersion, creatorSub, warehouseIds, lineSnapshotSha256})`; unique `documentId` allows only one request. Decisions require `recordDecisionIntent` with different active approver, matching scope, task ID and version; `createFlowableDecider` drives engine and `reconcileApproval` syncs state. `confirmApproval` checks current scope and snapshot and transitions approval in caller transaction; `cancelRequest` does not accept approved requests.
- Catalog (`contexts/catalog/infrastructure/prisma-repos.ts`, `prisma/schema.prisma`): `catalog.product_variant_uom.factor_to_stock_uom` is authoritative, stock row has factor 1; packing is not conversion source. Batch stores `expiresOn` and `qualityStatus` (`available`, `restricted`, `inspect`); new batch defaults to `inspect`.

## Contract deviations requiring explicit treatment

- `platform/persistence/transaction.ts` defaults to Serializable; R3 forbids that for trading confirm. Use a trading-specific caller-owned ReadCommitted unit of work with ordered row locks; leave platform pipeline unchanged.
- Bridge `cancelRequest` only transitions requested/starting/pending/decision_pending. R1 also requires cancellation after approval: add `cancelApprovedRequest` as a separate owning-module accessor using the bridge's `transition` + `auditApproval` in the caller transaction; do not write approval state directly. The engine is already complete on approved state.
- Bridge approval state changes do not update `trading.document.status`. Confirm must consume bridge-approved state without assuming document is already `approved`; document remains `pending_approval` until confirm. Record this divergence in final evidence.
- Bridge snapshot contract takes `quantity: number` (JSON hash); stock quantity and movement remain Decimal. Convert only at hash boundary after Decimal validation; do not use JS number for stock arithmetic.

## Implementation notes / deviations

- R3: lock document row first using `FOR UPDATE` before editing normalized lines. This prevents a concurrent confirm from hitting the confirmed-line immutability trigger before its version check. `tradingUnitOfWork` uses ReadCommitted, sorted balance-row locks, aggregated issue demand and the existing Inventory port; no Serializable isolation or change to the Inventory internals.
- R1: the bridge's reconciler changes `approval_request.state` but not `trading.document.status`. The issue stays `pending_approval` until confirm; confirmation requires bridge state `approved`, same saved-line hash, and fresh membership scope through `confirmApproval`. Reconciliation runs in the worker before confirm; the bridge confirm callback is a no-op because network access inside the document transaction would break atomicity. A pending decision returns 409 until worker reconciliation finishes.
- R2: draft response includes server-computed `stockQuantity`; at submit/confirm, lines are overwritten with stock UOM and the entered packing quantity is no longer stored. The bridge's numeric hash contract requires guarding quantities larger than `Number.MAX_SAFE_INTEGER / 1000`; larger values return typed 422 instead of silently losing precision.
- R6: `apps/dx-lab/server.js` is still a plain-text P11 stub, with no Next.js UI runtime or browser auth setup. Actual ERP Next.js UI already owns `/trading/*` per ADR 0016, so the shared form was placed in `app/trading/`, not in the stub. Catalog lacked a variant-UOM read endpoint; added the owning module's GET accessor `/api/v1/variants/{id}/uoms` for the picker. This is an intentional departure from the file plan. Browser UI behavior and DX-Lab integration remain unverified.
- No batch is created by trading. Batch picker lists only existing catalog batches. Corrections use the existing same-type confirmed-source link, with no automatic reversal.

## Proven acceptance checks

- AC-03: draft pack quantity 2 × factor 10 stores stock quantity 20.000 at confirm; balance 20.000, one movement, one audit and one outbox; version increments once. Replay of confirm with same key returns original response, new key with stale version yields 409, direct duplicate `(source_line_id,kind)` fails `P2002`.
- AC-04 service-level path: receipt 20.000, issue 12.000 submitted through `createRequest`, started through real Flowable starter, approved through `recordDecisionIntent` by distinct scoped actor, Flowable decider, and reconciler polling with deadline. Confirm posts −12.000 and balance 8.000; pending/rejected confirm produces typed 409 without movement. Both pending and approved cancellation tombstone the request in transaction. No approval state was seeded or written directly in test.
- Two-connection barrier race with two separately approved issues of 12 against 20: one succeeds, one gets typed 422 `INSUFFICIENT_STOCK`; balance 8, loser has no movement and unchanged status/version. Reverse line order across two batches also returns one success/one 422 without deadlock. Repeated local harness runs passed. Two same-batch lines totaling more than balance fail with requested/available details, zero movement.
- Two confirms racing on the same receipt: document-row lock serializes normalization; winner posts once, loser receives typed version 409 instead of raw immutable-line trigger error.
- Multi-line rollback: injected third receipt movement failure rolls back prior movements/balance/status/audit/outbox. Approved issue with third line on empty balance fails typed 422 before any movement, retains approval/status/version; replenishment then retry with same previously failed key succeeds. Draft with zero lines is allowed but confirm typed 422; stale PATCH typed 409; expired and quarantined batches typed 422; after submit, editing catalog packing factor does not alter issued stock quantity.
