# P07-T06 — Stocktake and sale record evidence

## Step 0: code findings before feature edits (2026-11-23)

1. `MovementKind` and database CHECK already support `stocktake`. `adjustStock` accepts either signed nonzero delta for that kind, rejects overdraft on negative deltas, creates missing balance rows for positive deltas, and anchors uniqueness on `(sourceLineId,kind)`. Product/archive and warehouse/archive checks still apply; quality/expiry checks run only for `issue`.
2. T02 `validate_confirmed_document` requires `counted_quantity IS NOT NULL` for stocktake; it does not demand `quantity IS NULL`. Keep stocktake `quantity` null. `guard_line` permits updates to lines created before confirmation within the same transaction only when status remains draft; normalize counts before transition.
3. Existing document number is capped at 64 characters in `ck_trading_document_number_length`; `requireText` trims and bounds text, while trading routes use typed `DomainError` 422. No existing buyer reference field has a runtime length rule; use 64 characters as the nearest document-reference convention, with a dedicated `BUYER_REF_TOO_LONG` error.
4. T03 `convertToStock(quantity,uomId,variant.uoms)` rounds HALF_UP to three decimals and supplies stock UOM. It rejects zero with `QUANTITY_NOT_POSITIVE`; stocktake legitimately counts zero, so extend conversion with a stocktake-only zero allowance rather than bypass UOM membership/rounding.
5. Internal events use JSON schemas in `contracts/events`, `serializeDomainEvent` registry and traceability destination. T05 extended the receipt schema for zero-line events. New stocktake contract must include all lines, including zero variance.
6. `guard_detail` checks sale issue purpose at insert/update; deferred `validate_confirmed_document` checks confirmed issue and copied lines. `createTradingRepos.getAggregate` includes issue purpose/status/lines; `lockDocument` locks by id; warehouse scope is checked in application services. Active-link uniqueness uses deferred triggers for transfers and receivings.

## Implementation decisions and deviations

- Approval condition R3 is closed: D06 specifies Flowable only for goods issue. No stocktake approval threshold or workflow exists. **Accepted self-confirm risk:** a counter may also confirm a found-stock adjustment. Action policies separate create/read/update/confirm/cancel; document creator, confirmer, audit and all variance lines remain recorded for later threshold design.
- Stocktake normalizes counted quantity and UOM within the confirm transaction, before the draft-to-confirmed transition required by T02 immutable-line guard. Zero is allowed through T03 conversion only for stocktakes. Sorted balance locks include missing rows as zero; positive delta creates missing balance. Post-check compares final balance to counted. `document_line.quantity` stays null. Snapshot for every line lives in the stored `trading.stocktake.confirmed.v1` outbox payload, including zero deltas. This internal event extends the T05 contract registry pattern; traceability is its only destination.
- Unlike goods receipt/issue confirmation, stocktake accepts expired, inspect and restricted batches because physical counts must record observed stock; it never changes quality status. The existing Inventory port's quality and expiry checks apply only to issue movements. Variant and warehouse must still be valid and active.
- Sale uses a deferred active-link constraint on both detail and document status changes, following transfer/receiving. The named invariant is **one active link per source**: cancelled draft releases its issue; confirmed sale occupies it permanently. Sale create copies every issue line, defaults `sold_at` to server now, and bounds opaque `buyer_ref` to 64 trimmed characters. Confirm rechecks issue and scope; service has no Inventory port, emits exactly one traceability outbox row, and never includes `buyer_ref` in any event.
- `downstream.impact.v1` and every federation relay are deferred to P09. No partner identity can be inferred from an opaque buyer reference.
