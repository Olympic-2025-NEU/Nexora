## Implementation and contract notes

- Reconciliation checks bound process instance ID and definition ID, then `historyDecision` compares decision, approver, request timestamp (the stored decision nonce) and rejection reason. No latest-definition lookup drives reconciliation. Trading CAS and bridge terminal transition commit in the same local transaction; a failed CAS keeps bridge intent pending and records an anomaly. Duplicate deliveries cannot repeat the transition. Rejected documents cannot confirm; approved documents can cancel with their request.
- Cosmetic fixture v2 changes only process name. Keep process key `goods-issue-approval`, task key `approveGoodsIssue`, candidate group `approver`, and completion variables `decision`, `decisionReason`, `approverSub`, `decidedAt` stable across genuine BPMN upgrades. Changing task/form key, group, or variable names can silently break task discovery or correlation.
- No expiry in v1: app-only timeout leaves a live engine task; auto-cancel invents an unappointed decision maker. Correct future expiry needs BPMN boundary timer coordinated with local request. Inbox shows age.
- Disposable Flowable battery exercises rejected terminal sync, duplicate reconciliation, conflicting history audit, cancel-before-worker, simulated transport outage at start and decision dispatch, recovery on real engine, and v1/v2 process history plus inbox. Outage is simulated by refusing transport calls while real Flowable remains running; process is **not** actually stopped. A decision cannot be recorded while the initial task has never been created: after start recovery the task exists, and the second outage covers decision intent.

## Addendum (2026-11-23): live-stack journey and compose env fix

- First live run of the gateway journey on a real stack (instance B) failed at the approver inbox step: GET /api/v1/approvals/inbox returned HTTP 500. ERP log: "Invalid Flowable configuration" from FlowableClient.fromEnv — deploy/compose.yml passed FLOWABLE_BASE_URL / FLOWABLE_ADMIN_USER / FLOWABLE_ADMIN_PASSWORD only to the worker service, not to erp, whose approvals composition root builds a FlowableClient at request time.
- Fix: the same three env entries are now passed to the erp service in deploy/compose.yml (commit "fix(p07-t07): pass Flowable client env to erp service").
- Security decision (recorded explicitly; LLM Council review 2026-11-23): the erp service now holds the Flowable REST credential. Accepted for this scope — Flowable exposes a single REST credential shared by all consumers, the worker already held it on the same internal Docker network, and that network is the security boundary. Recorded follow-ups (post-competition hardening, not in this task): fail-fast startup validation instead of a per-request throw; lazy/split client construction so read-only inbox queries do not require an engine client; a scoped non-admin Flowable identity; a shared compose env anchor so the entries cannot drift.
- Known gap: deploy/instances/a.env lacks the FLOWABLE_* keys entirely (pre-existing since P04-T05), so instance A would still interpolate empty values; instance B carries all keys. Left untouched here.
- Process note: this fix was executed by Milo under LLM-Council + LangGraph orchestration at the team lead's direction (2026-11-23) because the OpenCode implementer was unavailable (OpenAI credits exhausted). Milo's independent verification below still gates the merge.
- Live verification after the fix: erp recreated with the env present in the container; approver inbox smoke returned HTTP 200; the full gateway journey (deploy/scripts/journey-p07-t07.mjs) printed "AC-12 gateway journey: PASS" — creator submitted, a different approver saw the task in the inbox, self-approval returned 403, the approver's decision returned 202 (decision_pending), the document synced to approved, confirm moved stock exactly once. The trading battery was re-run after the fix (25/25). The workflow battery was not re-run: it passed on identical application code earlier the same day and cannot exercise compose env wiring; re-running it would require wiping the live Flowable history the journey had just produced.
