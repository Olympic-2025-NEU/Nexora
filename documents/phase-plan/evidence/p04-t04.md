# P04-T04 — Event handlers and ownership

**Date:** 2026-11-20. **Branch:** `phase04/p04-t04-event-handlers`.

## Implementation and decisions

- D1: `composition/event-handlers.ts` builds destination-only handlers for `traceability` and `federation`. Each routing wrapper checks `(eventType, schemaVersion)` and payload before invoking a destination-specific consumer. The platform dispatcher has no composition or trading dependency. Router logs message/correlation IDs, event type, schema version, destination, outcome and failure reason without logging payloads.
- D2: `PermanentDeliveryError` has code `NON_RETRYABLE`; the dispatcher dead-letters it on attempt one without retry/backoff and stores its reason. The four reasons are `UNSUPPORTED_EVENT_TYPE`, `UNSUPPORTED_EVENT_VERSION`, `INVALID_EVENT_PAYLOAD`, `NO_CONSUMER_REGISTERED`. Plain/transient failures retain T03's capped full-jitter retry and max-attempt policy. Unknown destinations retain `UNKNOWN_DESTINATION` retry. Unknown-version evidence is an attempt-one dead-letter row, structured router/dispatcher logs and the existing worker dead-letter count; dashboard/alerts belong to T07.
- D3: No ledger or migration. The port contract requires at-least-once consumers to dedupe by `payload.eventId`, upsert by source document ID + version and guard stored versions against stale replay. PostgreSQL reference-consumer tests demonstrate duplicate delivery produces one effect and replaying v2 after v3 cannot regress state. Production maps contain no consumer implementations until P08/P09; test consumers are reference implementations, not a Trace projector or federation sender.
- D4: Both production destinations have routing handlers with empty consumer maps. A known valid event without a consumer becomes an attempt-one `NO_CONSUMER_REGISTERED` dead-letter, never a delivered row. T03's `retryDeadLetter` requeues it after a consumer is registered; the suite exercises this replay. Permissioned admin retry API/audit, dashboards and retention remain T07/P12.
- D5: `contracts/events/registry.ts` imports the five P00 trading schemas directly, compiles Ajv validators once, fixes `schemaVersion: "1"`, fan-out defaults and destination constants. The serializer validates inside the command transaction before `ctx.emit`, so invalid emit fails the command and leaves zero outbox/audit rows. The router validates again as a backstop. JSON imports compile into `worker/dist/contracts/events/`; no runtime schema reads or Dockerfile changes. `workflow.*` belongs to T06 and is deliberately absent. Internal event versioning differs from federation envelope version `"1.0"`.
- D6: T03's open decision is **CONFIRMED**: a dead-lettered predecessor does not block successors. Consumers must detect aggregate-version gaps and version-guard upserts so later replay cannot regress newer state. Reference-consumer tests observe a jump and a stale replay.

**Plan/repo-reality deviation:** The plan states all five trading schemas require `documentId` and `documentVersion`. P00 schemas actually require these fields only for receipt and issue; transfer uses `transferId`, receiving uses `receivingId`, sale uses `saleId`, and these three have no payload document version. Their port contract uses the schema-specific source ID plus outbox `aggregateVersion` as the natural key/version guard. The reference version-guard test uses the receipt schema, which has both payload fields. Schemas and locked fixtures were not changed. The repository's SPDX source-inventory check also required refreshing `evidence/source-inventory.json` for authored TypeScript files.
