## 4. Gateway request traces

Against the source clone's gateway:

- `POST /api/v1/core/records` without a token → **401** from the gateway.
- The same request with a real dev-staff access token → **401** JSON,
  code `TOKEN_INVALID`, with a request id
  (example `de0089bf-c50a-4aec-b601-c1fa8fff96fa`).

Issued tokens carry `aud: "account"` because the realm template defines no
audience mapper, while core-data requires the configured audience — the
platform correctly defaults to deny. A live success-path trace (200/201) is
therefore **not proven at this gate**; the fix belongs to the identity phase
(add the audience mapper to the realm template for the browser clients).
The records/evidence behaviour itself is proven by the integration suites
in §2.

## 6. Host incident during the run (environment, not a product defect)

The host disk was 99% full (about 1.8 GB free on a 159 GB volume).
SeaweedFS refused to allocate new volumes for the private bucket ("No
writable volumes"), so scan promotion initially failed with
`FILE_STORAGE_ERROR`. After freeing space (Docker build-cache / container /
volume prune and removal of stale user caches, including a 13 GB
crash-dump cache), the same uploads scanned clean and the drill passed.
Recommendation: keep at least 15 GB free on the demo machine.

## 9. Follow-up (2026-11-19): Keycloak audience-mapper finding fixed

The platform finding recorded in the P03-T07 evidence (real Keycloak tokens carried aud="account" only, so the core-data API rejected them with 401 TOKEN_INVALID) is fixed by commit 2ed4540 on branch fix/keycloak-audience-mapper: an oidc-audience-mapper (included.custom.audience=erp-browser) was added to the erp-browser and dxlab-browser clients in deploy/keycloak/realm-template.json.

Verified live on 2026-11-19 on a clean clone of that branch (bootstrap from the repo template, no temporary runtime mapper): smoke 8/8; a real password-grant token for the dev user carried aud=["erp-browser","account"]; upload reached scan_state clean; POST /api/v1/core/records through the gateway returned 201; GET of the created record returned 200. The live gateway success trace that §7 could not prove at gate time is now proven.
