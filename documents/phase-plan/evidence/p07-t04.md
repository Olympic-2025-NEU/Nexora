# P07-T04 — Partner transfer evidence

## Step 0: checked before feature code (2026-11-23)

- `platform/outbox/message.ts`: `OutboxEventInput` carries aggregateType, aggregateId, aggregateVersion, eventType, schemaVersion, payload, destination, correlationId. `runCommand` collects `ctx.emit` events; `appendOutbox` inserts after domain in the same transaction and generates a fresh UUID for each outbox row. Row has JSONB payload, status (`pending` default), attemptCount (0), nextAttemptAt (now), lease, lastErrorCode and deliveredAt. No hash or metadata column; envelope `messageId` must be generated at confirm and persisted inside payload. Hash storage is deferred to P09; JCS SHA-256 can be recomputed from the stored payload.
- **Design deviation / loss prevention:** `composition/event-handlers.ts` registers a federation destination but *no federation consumer*. The router throws `PermanentDeliveryError('NO_CONSUMER_REGISTERED')`; `platform/outbox/dispatcher.ts` dead-letters immediately, without retry. Unknown destination alone retries with backoff, but federation is a registered destination. Thus the plan's ordinary offline retry assumption does not apply. Existing dispatcher only claims `pending`/`retry_due` rows when `next_attempt_at <= now()`. Hold federation announcement with `status=pending`, `attempt_count=0`, `next_attempt_at=9999-12-31T00:00:00.000Z`; never dispatch it before P09 registers a consumer and explicitly schedules it. The writer needs a narrow optional scheduling field on `OutboxEventInput` to write this existing column atomically; no dispatcher rewrite or new database column. Test must assert a real dispatcher tick leaves the row untouched.
- `event-payloads-v1.md`: envelope fields schemaVersion, messageId, eventId, eventType, issuerInstanceId, recipientInstanceId, occurredAt, publishedAt, correlationId, causationId, sourceDocument `{type,id,version}`, lots with `{sourceLineId,originLot:{issuerInstanceId,lotId},senderBatch:{instanceId,batchId},product:{instanceId,productId},quantity,unit}`, upstreamReferences, evidence, sharingPolicyVersion. Transfer additionally requires `linkedIssueId` and `sentQuantity` equal to summed lots; each sourceLineId is a *transfer* line ID. Decimal fields are strings; unknown fields rejected; JCS SHA-256 defines payload hash.
- T03: `composition/trading.ts` serializes receipt/issue domain events via registry; `documents.ts` calls `ctx.emit`, uses `createTradingRepos(tx)`, checks warehouse scope and locks document row before versioned transition. `application/http.ts` uses `runCommand`, `tradingUnitOfWork`, `mapRouteError`, `If-Match` and mandatory confirm key. `platform/access/policy.ts` registers each explicit trading action. Routes delegate through `contexts/trading/index.ts` to thin shared handler.
- M01: `contexts/system/infrastructure/prisma-repos.ts` reads partner by ID with connection status; `system.partner` has issuerInstanceId, code, displayName, status (`active`/`suspended`). `PartnerConnection` has endpointUrl, outboundTokenUrl, outboundClientId, outboundSecretRef, outboundAudience, inboundClientId, allowedInboundScope, status, lastVerifiedAt, rotatedAt. Endpoint exists but T04 does not call it.
- Server-only config: `deploy/config.mjs` validates service env at startup, while `composition/trading.ts` builds service/ports. New `NEXORA_ISSUER_INSTANCE_ID` belongs to trading composition and must fail clearly when composition is created. It is not the Keycloak issuer or organization ID.
- Further contract discrepancy: `event-payloads-v1.md` describes internal `trading.transfer.confirmed.v1`, but R7/API demand exactly one `transfer.announced.v1` outbox row per confirm. T04 persists federation envelope directly; an additional internal outbox message would violate the one-row requirement. Also T02 line DB field is `source_issue_line_id` (not `source_line_ref`); transfer copy uses the FK field, preserving exact line linkage.

## Deferred / known limitation

P08/P09 own consumer, release/scheduling, ACK, retry/delivery and hash storage. T05 owns receiving confirmation. A confirmed transfer with no deliverable recipient occupies the issue permanently; delivery_state remains pending until federation support arrives. Correction of an issue never cascades to an earlier transfer; snapshot refers to the original confirmed issue.
