## Step-0 finding: issuer identity was not wired on the live stack

`NEXORA_ISSUER_INSTANCE_ID` was read by `composition/trading.ts` but never set in
`deploy/compose.yml`, so on a real deployment every transfer/receiving route would throw
"NEXORA_ISSUER_INSTANCE_ID is required" (the batteries set the variable in-process and
could not catch this — the same gap class as the P07-T07 Flowable env bug).
Fix (67e879f): erp service now receives `NEXORA_ISSUER_INSTANCE_ID: ${INSTANCE_ID}`.
Verified after the gate: with no override, the running erp reports its instance id `b`.

## Gate chain (spec chain, with one correction)

Spec correction recorded: the phase plan's chain omitted C's goods issue, but a sale
record legally requires a confirmed goods issue with purpose `sale`. The executed chain
restores that step: C receiving → C issue (sale) → C sale record.

Venue: the single live instance-B stack (PostgreSQL + Keycloak + APISIX gateway +
Flowable 8.0.0), three parties played by switching the erp service's
`NEXORA_ISSUER_INSTANCE_ID` between legs (gate-a / gate-b / gate-c) via a /tmp compose
override; repo env files untouched. Every leg ran through the gateway with real
Keycloak tokens; every issue was created by journey-creator and approved by
journey-approver (creator ≠ approver) through the real Flowable inbox/decision API.

Real vs simulated, honestly: federation TRANSPORT is simulated — each
`transfer.announced.v1` envelope was taken byte-for-byte from the emitting leg's real
outbox row and seeded into `platform.inbound_message` with its JCS SHA-256 payload hash
(the receiving leg's create then re-verified the hash server-side and passed). Instance
identity via deployment env is exactly how separate production instances differ; the
self-transfer and recipient checks were genuinely exercised at every hop. Cryptographic
message authenticity remains P08/P09 scope, as ruled in T05.
