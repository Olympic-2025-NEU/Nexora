## Contract boundaries and follow-up

`approver` is a Flowable candidate-group string. T05 does not synchronize it with Keycloak or establish a user's warehouse permissions. T06 must authenticate and authorize the actor in the ERP application before calling the engine. Flowable's businessKey is not unique: `startProcess` and `completeTask` do not retry POSTs, and network/timeout failures become `FlowableUnknownOutcomeError`. T06 must query by businessKey and task/history before any retry, using local uniqueness and a worker lease; a duplicate businessKey is treated as an error. See [workflow spec §2/§4](../workflow-spec-v1.md).

Flowable REST admin is published on loopback for deployment and tests, and on the internal Compose network for the worker; it has no APISIX route. On first boot a fresh database seeds the REST admin identity from the instance env. Later env changes do not rotate that identity; rotation requires resetting the Flowable database and loses process state unless migrated. The P03 backup/restore drill does not yet cover the Flowable database. Extend and verify that drill at G04/P12 before claiming durable recovery; restarting the container alone is not a backup test.
