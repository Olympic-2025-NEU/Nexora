# P04-T02 — Idempotency for write commands

**Date:** 2026-11-20. **Branch:** `phase04/p04-t02-idempotency`.

## Implementation

- `20261120000000_platform_delivery_idempotency` creates the blueprint-exact `platform.idempotency_record` with unique scope, state and SHA-256 CHECK constraints, expiry index, and `app_runtime` SELECT/INSERT/UPDATE/DELETE grants. The migration was authored directly in the Prisma Migrate directory and applied with `prisma migrate deploy` rather than generated by `prisma migrate dev`; it remains the only migration source. `core_data` receives no grant.
- `runCommand` validates the 16–128 character key, hashes the parsed `CommandOptions.payload` using JCS and SHA-256, and runs authenticate, resolve-tenant and authorize before lookup. A completed same-hash row replays its stored command result without domain work, transaction or dispatch. A different hash returns 409 `IDEMPOTENCY_CONFLICT`. An absent key retains the T01 path; a supplied key without an adapter fails closed.
- The Prisma adapter claims with `createMany({ skipDuplicates: true })` (PostgreSQL `INSERT ... ON CONFLICT DO NOTHING`), and completes inside the **same** domain unit-of-work transaction. Unique-index contention resolves by rereading the completed winner; the defensive unresolved response is 409 `IDEMPOTENCY_IN_PROGRESS`. Rollback removes the claim and effects together. Expired completed rows are conditionally taken over in the command transaction. `purgeExpired()` is available; scheduling belongs to P04-T03.
- T02 supersedes T01's reserve-before/complete-after port and its historical description in `evidence/p04-t01.md`. T01's step registry and six existing tests remain intact. No production route uses this adapter yet; the DB test is the reference consumer. Federation inbox deduplication remains separate in P09; Redis is not a source of truth.

## Verification

- `npm run test:platform:schema`: PASS on an upgraded Phase 02 database and a fresh database, including a repeat migration deploy, table/column/CHECK/grant assertions and restore check.
- `npm run test:platform:idempotency`: PASS, four PostgreSQL integration tests. Twenty callers all finish with the same response after their initial lookups are synchronized: exactly one audit effect, one dispatch and one completed idempotency row. Sequential retry and JCS key reordering replay without new effects; a different body maps to 409. Domain throw after claim leaves zero rows/effects; retry with a different body succeeds. Expiry takeover updates the stored result and `resource_id`; purge deletes only expired rows. Different actors with the same key execute independently.
- `npm run test:http`: PASS, 14 tests (six original T01 tests unchanged). Replay skips domain/commit/dispatch after authz; claim and completion use the domain transaction before commit; claim-loss rechecks and replays or retries once; invalid keys and conflict mapping are covered.

## Scope and defaults

- Outbox table and worker arrive in P04-T03. The T02 assertion for “no new outbox” is **effect exactly once plus dispatch exactly once**, not a literal outbox-row assertion. The literal row assertion remains for G04 after T03.
- Retention is **24 hours**. The blueprint's `failed` state is constrained but unused by T02: rolled-back commands leave no record. Defaults are `method = POST` and `routeKey = action`. `response_status` stays NULL; `response_body` stores the JSON domain result for verbatim replay at the command-result level. HTTP status remains the future route's responsibility.
- New source files required refreshing `documents/phase-plan/evidence/source-inventory.json` to make the default SPDX check pass. Dependencies did not change; `npm-license-inventory.json` did not need a refresh.
