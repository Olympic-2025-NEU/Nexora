# P03 file storage v1 — upload, quyền và reconciliation

## Ranh giới dữ liệu

- D02 dùng SeaweedFS 4.53 với bucket vật lý riêng cho `quarantine`, `private`, `public` mỗi instance. Bảng `platform.attachment.bucket` lưu **loại bucket**, không lưu tên vật lý. `core-data` giữ credential S3 nội bộ; browser/DX-Lab không nhận credential hoặc URL bucket private. Bucket không có public-read ACL. Core được `List` quarantine và private để dọn orphan; scanner chỉ được đọc/ghi quarantine và ghi private.
- `POST /api/v1/files` yêu cầu Bearer OIDC có chữ ký/issuer/audience hợp lệ, membership active thuộc instance, role Administrator hoặc Staff và `Idempotency-Key` 16–128 ký tự. Core tự xác thực lại; không tin header danh tính do client gửi. Gateway định tuyến cả `/api/v1/files` và `/api/v1/files/{id}` đến Core.
- T04 chỉ tạo tệp **chưa link owner**: `owner_type='core_record'`, `owner_id=NULL`, `visibility='private'`. `ownerType`/`ownerId` từ request và visibility khác private bị 422 cho tới khi T07 có policy owner thực. Không lấy tên file từ client làm S3 key. Key `pending/<UUID ngẫu nhiên>` không chứa tên, ID hay token.
- MIME v1: PDF, PNG, JPEG, UTF-8 plain text; kiểm chữ ký/UTF-8 và kích thước 1 byte đến 10 MiB. HTML/SVG/ZIP/executable và MIME khai sai bị từ chối. T04 chưa chứng nhận tệp sạch: object ở quarantine, metadata `scan_state='pending'`; scanner T05 mới quyết định `clean`/`infected`/`error` và chuyển object hợp lệ sang private.

## Thứ tự ghi và bù lỗi

1. Xác thực/phân quyền, parse multipart có giới hạn, SHA-256 bytes, kiểm replay trong PG theo hash của actor + route + key. Cùng key/cùng nội dung trả lại attachment ID; cùng key/khác nội dung trả 409.
2. PUT bytes vào bucket quarantine. S3 lỗi thì không tạo metadata. Sau PUT, một transaction PG tạo `attachment` và success audit cùng request ID. PG/audit lỗi thì xóa object bù; nếu thao tác xóa lỗi, ghi reason code và reconciler xử lý sau.
3. `file-reconciler` chạy khi profile `apps` bật, mỗi 15 phút. Nó xóa `pending/` quarantine hoặc `clean/` private object quá 15 phút **không có** metadata; nếu attachment `pending` quá hạn nhưng object mất, tăng version, đặt `error` và ghi audit cùng transaction. Chạy lại không tạo tác động thứ hai. Reconciler không tự promote file sạch hoặc xóa file có metadata.

## Đọc và vận hành

- `GET /api/v1/files/{id}` trả metadata cho uploader hoặc Administrator; người khác nhận 404 để không lộ sự tồn tại. `?download=1` chỉ stream khi row `clean`, bucket `private`, visibility `private`, actor có quyền và SHA-256/kích thước khớp metadata. Pending/infected/error nhận 423. Bytes trả với `Content-Disposition: attachment`, `nosniff`, CSP sandbox và `no-store`; successful download có audit. Không có presigned URL public ở v1.
- Backup DB và SeaweedFS phải cùng tập snapshot/manifest ở T06; attachment chứa checksum để so sau restore. T04 integration test dùng DB + bucket tạm riêng và volume tạm, kiểm compensation và restart. `npm run test:platform:files` chạy bài test đó; không dùng credential instance thật.
- T07 phải bổ sung owner link/resource policy, structured records và smoke qua gateway khi UI tắt. Cho tới lúc đó, file chưa gắn chứng từ/lô và không được gọi là evidence công khai.

## T05 — kiểm dịch và xử lý lỗi

1. `file-scanner` dùng credential S3 riêng để đọc object quarantine, đối chiếu SHA-256/kích thước với `attachment`, gửi bytes qua ClamAV `INSTREAM` (TCP 3310). ClamAV container chạy `freshclam` và giữ signature DB trong volume `clamav_data`. Trước demo/vận hành, kiểm `docker compose logs clamav` có cập nhật signature thành công; `scan_engine_version` lưu chuỗi `ClamAV engine/signature/date` cho từng kết quả. Chữ ký quá 7 ngày hoặc có thời điểm tương lai bất thường bị xem là lỗi và fail closed. Nếu scanner không trả verdict hợp lệ, **không** chuyển file sang private.
2. Worker claim row bằng version và lease 60 giây; tối đa 5 lần quét, retry sau 30 giây, 60 giây, 2 phút, 4 phút, với giới hạn 1 giờ. `scan_attempts`, `scan_error_code`, `next_scan_at`, `scan_lease_*` ở migration mới. Timeout, service down, storage fail và checksum sai chuyển `error`, giữ quarantine và audit `file.scan_error`. Khi hết 5 lần, `next_scan_at=NULL` và chỉ Administrator được yêu cầu retry thủ công. Lease hết hạn cho phép worker khác nhận lại; CAS ngăn ghi kết quả cũ.
3. Verdict `clean`: PUT sang private key ngẫu nhiên, transaction PG đổi bucket/key/state, ghi thời điểm/phiên bản signature và audit `file.scan_clean`, sau đó xóa quarantine. PG lỗi thì xóa bản private bù; reconciler xóa orphan nếu bù lỗi. Verdict `infected`: giữ quarantine, ghi `infected` và audit `file.scan_infected`; không có URL/download và không cho retry qua API. Admin kiểm tra kết quả trong metadata, có thể gọi `POST /api/v1/files/{id}/discard` để xóa bytes quarantine và giữ metadata/audit; thao tác lặp lại an toàn. Không mở quyền tải hoặc gắn evidence cho tệp đó.
4. `POST /api/v1/files/{id}/retry-scan` chỉ Administrator, chỉ nhận trạng thái `error`, body rỗng; reset attempt về 0, chuyển `pending` và audit cùng transaction. Cần object quarantine còn tồn tại. Người dùng thường không thấy mã lỗi nội bộ; metadata admin có số lần thử, mã lỗi, thời gian retry và thời điểm xóa bytes nhiễm. Upload replay cùng idempotency key trả trạng thái hiện tại của row.
5. `npm run test:platform:scan` dùng PostgreSQL, SeaweedFS và ClamAV tạm, EICAR ghép tại runtime, kiểm clean/infected/down/timeout/checksum/retry/admin/audit/URL unsigned. Bài test không dùng instance A/B/C. Sau khi đổi `deploy/seaweedfs/bucket-policy.json`, chạy lại `storage-bootstrap` và restart SeaweedFS để policy credential mới có hiệu lực.
